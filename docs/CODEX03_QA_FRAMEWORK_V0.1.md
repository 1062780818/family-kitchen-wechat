## 一、验收层级

| 层级 | 验收对象及执行动作 | 通过所需证据 | 第 0 阶段边界 |

| L2 | 初始化隔离测试库与迁移；启动后端、管理后台、小程序联调；检查健康、存储、基础连接 | 初始化/迁移日志、健康探测、连接验证、启动日志、停启后数据读取 | 只操作授权测试环境；后端缺失须如实失败或阻塞 |

验收层级不是“完成 L1 就等于 L7”。基线复现结论限定其实际检验范围；产品发布结论需满足完整发布范围。

## 二、基线复现步骤

1. 接收 Codex-01 的仓库 URL、分支、完整固定 Commit、子模块/LFS 信息及交付清单；验证文件正式交接。禁止自行选最新分支作为验收版本。
2. 在项目负责人授权的全新 QA 目录获取代码，检出指定 Commit 并记录 `git rev-parse HEAD`、`git status --short` 和实际来源；不要与 Codex-01 共用工作树或 node_modules/虚拟环境。可用独立容器/虚拟机，但不强制新增平台。
3. 记录 OS、CPU 架构、运行时、包管理器、数据库、微信工具版本、网络/代理与系统时间。采用独立依赖缓存或能证明无现成安装结果的干净安装；缓存设置按包管理器选择，不能硬编不存在的命令。
4. 先检查许可证、锁文件、脚本、配置样例。只填测试凭据，不把生产密钥写日志；只使用合成家庭 A/B 和授权测试 AppID/数据库。审查安装脚本副作用后按原说明安装，不预先修复失败。
5. 按 Codex-01 文档逐条运行安装、Lint、类型检查和测试；保存命令、退出码、日志及文件差异。文档没提供的命令记缺口并请求补充，禁止将手工猜测步骤算作复现一致。
6. 初始化全新隔离测试库、结构、权限规则和必要种子；执行文档中适用的迁移/重复启动，记录错误和清理方案。禁止在生产或其他员工数据库执行初始化/清空。
7. 对小程序、后端、管理后台分别安装/构建/启动；还原原服务依赖。每个模块记录“存在、缺失、未交付、需外部服务”，不可把某端启动代替全部成功。确实不存在且不属于候选范围的模块须给代码清单和审核后的 NA 理由。
8. 小程序导入和编译后连独立后端，管理后台通过实际入口访问；检查健康探测、授权测试登录和一条基础数据读写。只有构建成功但没有连接证据，L2 不通过。
9. 对照 Codex-01 每项结论记录一致/不一致，定位环境差异、漏写步骤、缺依赖或代码缺陷。原样失败与其后仅环境补丁的二次执行分开记录；补丁须有独立提交，绝不覆写原失败证据。
10. 输出限定范围的 PASS / CONDITIONAL PASS / FAIL；缺版本/环境/日志先记阻塞，不给通过结论。缺陷回传对应开发员工，修复后在新固定 Commit 重测。

## 七、人工真机测试建议

最小建议设备为一台实际使用的 iOS 和一台 Android（以用户实际设备及冻结支持范围为准），两个独立测试微信身份分别作为妻子/丈夫。记录设备、系统、微信版本、基础库、开发者工具版本、体验版 Commit 和后端部署版本；至少交叉执行一次双角色流程。若没有某设备则记覆盖缺口，不伪称全平台通过。

1. 双端首次登录/重新登录、未绑定引导、绑定和固定角色；取消授权、会话过期、切换账号，确认无串家缓存。
2. 妻子选多菜、三种分量、单菜及整单备注、日期餐次时间；丈夫看同一内容，标买菜并提换菜，妻子确认后完成接单→做饭→上菜→一次送亲亲；双端重启检查历史快照。
3. 分别在发送前、服务端处理后响应前断网；切后台、锁屏、杀进程、恢复网络；确认不丢单、不重单、不误显示送达。
4. 相册/相机授权拒绝、缺图、正常图、超限图、上传中断；观察输入是否可恢复和错误信息，不绕过服务端检查。
5. 微信通知授权/拒绝/真实收到/未收到/旧通知点击；对照真实内部状态，通知失败不阻断核心操作、不泄露他家数据。
6. 检查小屏、长菜名/备注、中文/表情、键盘遮挡、滚动与返回；亲亲动画失败或退出页面不影响数据，不强制视觉效果判业务成功。
7. 在实际体验/发布配置上复查合法域名、证书、登录配置、隐私说明、上传与通知能力等适用条件；以当时平台官方要求及实际账户能力核验，不预设必有订阅权限或必能审核通过。

每项保存脱敏截图/录像及关联接口/数据证据；无录像的理由须记录。不得把开发者工具模拟通过填作真机通过。

## 八、发布门禁草案

本节是 QA 建议，待 ChatGPT 冻结后纳入正式发布任务；本轮不更改主分支/CI 配置。

### 8.1 第 0 阶段门禁

- QA 框架：必需文档/矩阵/安全表/模板/边界/输入清单齐全；自检通过仅表示文档结构。本轮不因此宣告基线 PASS。
- 基线复现：版本确定、L0 合规可追溯、L1/L2 各模块成功或存在明确不通过/条件结论；缺项不掩盖。缺少代码、Commit、独立日志时不得 PASS。
- 原基线尚无新需求功能：记复用适配差距，不因为没实现新增亲亲机制等直接认定原有构建不可复现；也不能因此认可未来产品已达标。
- 阶段推进由用户与 ChatGPT 根据三方报告决定，Codex-03 不自行启动正式业务开发。

### 8.2 第一版发布门禁

1. 范围和需求冻结，阻断范围内的 DR 已决策；每项必测用例有结果和证据，NOT_RUN/BLOCKED 不得折算成功。
2. 发布候选固定 Commit、锁文件、配置/规则版本、构建产物哈希可追溯；独立干净构建和适用的 Lint/类型检查/测试有日志。不存在检查时由 ChatGPT 明确是否接受替代，不能用空脚本假通过。
3. 必测核心多菜→调整→做饭→上菜→亲亲，以及异常重试、权限/家庭隔离通过；数据库与 UI 结果一致；Mock 结果不可覆盖真实联调缺口。
4. 未关闭 S0=0，未关闭 S1=0；任何 S0/S1 未关闭都不得通过。S2 逐项交 ChatGPT 决定是否阻断，记录目标版本、风险、绕行、责任人和处理期限；无明确决定不放行。S3/S4 入优化清单。
5. 安全合规、无已知阻断漏洞/可用密钥泄露；许可证及来源问题关闭；适用的数据库/文件权限用真实客户端身份验证。
6. 双角色真机流程完成；外部通知不可用时仍验证内部状态。微信通知降级是否满足本版目标由 ChatGPT 结合已确认“尽可能”要求判定，禁止以无法保证外部送达伪造成功。
7. 授权测试环境完成数据备份/恢复与回退演练；回退涉及 Schema 兼容时提供具体可行步骤，不能只说“回滚代码”。测试数据与生产隔离，日志脱敏；发布动作另需负责人批准。
8. 回归对应最终 Commit；任何影响代码/依赖/规则/配置的后续改动使受影响结论失效，重新执行相关回归。由 03 签署，01 只集成已获批准的版本。

### 8.3 结论判定

| 结论 | 使用条件 |
| --- | --- |
| PASS | 明确验收范围内必需证据齐全、必测通过、无 S0/S1、无阻断 S2、无未决发布阻塞；列出未纳入范围内容 |
