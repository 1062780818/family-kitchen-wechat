## 2. FK-C03-003-01｜S1｜已修复待复验

### 根因

原 `prisma.order.update({ where: { id, status } })` 在真实 MySQL 竞争请求下不能把“读到旧状态”和写入结果可靠地表现为一次条件更新结果；两个请求都可能返回成功，并分别进入后续通知逻辑。

### 修复

- `OrderService.updateWithExpectedStatus` 改用 `updateMany({id,status:expectedStatus})` 发出数据库条件更新，并只接受 `count === 1`。
- `count !== 1` 固定返回 `409 / ORDER_VERSION_CONFLICT`；成功后再读当前餐单。
- 通知和其他业务副作用仍在条件更新成功之后，因此竞争失败请求不会执行通知。没有增加单进程锁，也没有依赖前端禁用按钮。
- 不同状态操作仍由状态机判断；已完成操作的普通重复请求不会被误认为新的成功执行。原 `prepping` 端点只作为现有代码的“做饭中前置状态”并发样本，本轮没有把它恢复为目标产品主状态。

### 真实证据

MySQL 8.4.10 上的脚本 `tests/integration/foundation-defect-regression.mjs` 为 `19/19 PASS`：接单竞争为 `200 + 409`，接单通知记录数为 `1`，状态为 `accepted`；进入 `prepping` 的竞争为 `200 + 409`，完成后重试为 `400`，最终状态为 `prepping`。这同时检查了响应、数据库状态和业务记录数量，不以“第二个响应不是 200”单独冒充修复。

## 3. FK-C03-003-02｜S1｜已修复待复验

### 根因与影响路径

上传合同同时返回稳定 `key` 和临时 `url`，但菜品、动态、上菜图和头像消费者把 `url` 当永久字段回写。私有桶 URL 过期后，业务数据失去可展示图片。受影响保存／读取路径包括：菜品 `imageUrls`、餐单 `servedImageUrls`、餐单菜品快照内 `imageUrls`、动态 `imageUrls`、用户 `avatarUrl`，以及相关小程序 API 适配和四个上传页面。

### 修复

- 业务字段长期保存 `family/{familyId}/{category}/{date}/{uploader-random}.ext`；临时 URL 只用于当次预览。
- 菜品新增／编辑、餐单上菜、手工动态和家庭头像写入前，在服务端校验 JWT 用户、当前家庭、资源分类与对象存在性；签名 URL 和被篡改 key 不能再写入这些家庭图片字段。
- `GET /storage/url?key=...` 每次重新核验身份和家庭，再对真实存在对象签发短时 URL。签名期限可配置但被限制在 `1..900` 秒，未改公开桶、永久地址或关闭鉴权。
- 删除仍要求同家庭上传者，并新增菜品、餐单、快照、动态、头像引用检查；引用中对象返回 `STORAGE_OBJECT_IN_USE`。
- 小程序 API 层把稳定引用保存在 `imageRefs`／`servedImageRefs`／`avatarRef`，展示字段按需鉴权换新；上传页面改为提交 `key`，预览仍可用当次 `url`。
- 对已有错误值提供 `migrate-storage-refs` 的 preview/apply/rollback。它只处理可信 MinIO 来源、家庭／分类／上传者归属可核实且对象存在的记录；不下载外部 URL，不猜归属，不删除无法识别数据。应用前创建不可覆盖备份，应用和回退都在事务内检查当前值，避免覆盖迁移后的新编辑。

### 真实证据

MinIO 私有桶回归验证：2 秒 URL 过期为 403；同家庭鉴权重取和对象读取均为 200；跨家庭重取为 403；重复编辑保持稳定 key；服务重启后仍能从数据库 key 重取。迁移工具在隔离库完成 `preview(1) → apply → rollback(1) → apply`，最终值为稳定 key。

授权边界仅证明“通过当前 API、JWT 家庭上下文和私有桶配置”的访问控制；没有声称可抵御 MinIO 管理凭据泄露、主机入侵或生产网络错误配置。
