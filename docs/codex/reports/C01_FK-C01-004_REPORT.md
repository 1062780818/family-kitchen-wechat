## 3. 最新规则的数据与接口影响

以下均为后续技术草案边界，不是本轮正式schema实现：

| 域       | 保留／新增                                                       | 明确不建                                         |
| -------- | ---------------------------------------------------------------- | ------------------------------------------------ |
| 菜品     | `kissPrice`默认1且可独立设置；正式菜基本资料                     | 亲亲余额、支付／收款属性、分量价格               |
| 餐单     | `mealDate`、`mealSlot`、预计时间、整单备注；同餐位进行中唯一保护 | 分量／规格、亲亲送达或支付状态                   |
| 餐单明细 | 菜名、亲亲价格等不可变快照；单菜备注；逐菜评价关联               | 分量、送达确认、当前菜价覆盖历史                 |
| 愿望清单 | 与餐单／菜谱独立；菜名、图片、参考链接、家庭归属                 | 本餐临时行、报价、菜数／亲亲合计、自动转菜谱     |
| 调整     | 提案版本、妻子确认版本、请求幂等                                 | 旧提案覆盖新提案；通过重复餐位接口修改进行中菜单 |
| 评价     | 每明细可选三档；整单一句话可空；不强制                           | 星级、自动评价、奖励、评价改变订单状态           |

同餐位唯一不能仅“先查再新增”。原MySQL路线可采用独立活动餐位占位表并对`familyId + mealDate + mealSlot`设唯一键，在餐单事务中创建／释放；CloudBase路线可使用相同组合派生确定性活动文档ID并在服务端事务内处理。已上菜不属于进行中状态，释放槽位；重复请求仍通过独立幂等键返回原结果。

## 5. 工程／安全证据复核及分类

沿用C01-003的实际证据，规则变化没有把失败变成成功：

- `admin/`是Vue Web管理后台，其生产构建仍有18条TypeScript诊断；`backend/`是Nest后端，生成Prisma Client后可构建和启动，但Jest仍有5套件／46用例失败。二者未混称。
- 根Lint／test失败、typecheck漏检；本轮没有关闭检查、删测试或做全仓清零。
- `storage.service.ts`仍会设置全桶公开读；C01和C03均实测匿名GET 200。共享仓库未发现公网部署配置，本轮不部署、不上传真实照片，也未擅改正式存储实现。

分类保持：图片家庭权限、可信身份／角色／幂等和最终有效质量门禁属于两路线都必须解决；原Nest失败测试、Prisma漂移、后端依赖和通知／WS属于保留原后端时解决；Web管理后台、爱心币／成就／AI／复杂消息属于待范围确认后不部署或删除；微信／CloudBase真实能力属于缺环境待验证。

最新规则另使下列旧模块明确成为删除候选：`LovePointLog`及余额／流水API、亲亲打赏消息、自动评价Cron、星级结算／奖励，以及任何未来误加的分量和亲亲送达模型。删除须在正式任务中做依赖分析和C03回归，本轮不直接删源码。

## 6. 架构结论

推荐仍为“精简原独立后端”，但不是正式切换决定。原因仍是证据等级：原后端安装、迁移、服务和部分业务链由C01实际运行并经C03独立复现；CloudBase只有官方能力分析和本地13项模拟，尚未证明真实身份、规则、跨实例事务或真机。

新规则缩小了两路线的目标模型：删除分量、亲亲送达和菜单外本餐报价，新增独立愿望清单、逐菜评价及餐位唯一。两路线都受益，但不会消除CloudBase需重写16个前端API、JWT／服务层、Prisma迁移、上传、通知和WS的额外成本。完整部署、费用和风险比较继续以`C01_FK-C01-003_REPORT.md`为准，其官方资料查询日期为2026-09-07。

本轮不切换架构、不删除原后端。如果ChatGPT最终选择CloudBase，应先用隔离环境真实验证四能力和同餐位并发，再决定迁移。
